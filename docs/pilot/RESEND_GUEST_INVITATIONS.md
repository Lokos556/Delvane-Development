# Resend guest invitations

Delvane sends through the existing approval and delivery queue on schema 3091. Resend's `POST https://api.resend.com/emails` uses the existing invitation version as the idempotency key and returns the provider email ID. Delvane saves the rendered email in the encrypted envelope so a retry uses the same content even after a restart or template change. The Hungarian and English templates use Delvane's yellow, white and black palette in HTML and include plain text and one secure link per guest. Booking contacts currently have no language preference, so the default is one bilingual message. [Send Email](https://resend.com/docs/api-reference/emails/send-email) · [Idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys)

The Ireland region applies to sending from `mail.delvane.app`. The API host remains `api.resend.com`. Resend documents that message content, delivery logs and webhook payloads are stored in the United States. Use fictional data and the owner's test mailbox for this trial. Keep click and open tracking off in **Domains → mail.delvane.app → Configure** to preserve the direct guest link and avoid tracking pixels. [Resend data location](https://resend.com/security/gdpr) · [Domain tracking settings](https://resend.com/blog/introducing-custom-tracking-domain)

## Runtime setup

Configure these settings for a disposable UAT instance with synthetic data. The guest hostname is separate from the sending domain and must be approved and provisioned before testing.

| Environment variable | Value |
| --- | --- |
| `DELVANE_GUEST_EMAIL_PROVIDER` | `resend` |
| `DELVANE_GUEST_EMAIL_ENABLED` | Leave unset or `0` during setup. Set to `1` when ready to approve the test invitation. |
| `RESEND_API_KEY` | The existing domain-restricted **Delvane Guest Invitations** key. |
| `RESEND_FROM_EMAIL` | Optional. Defaults to `checkin@mail.delvane.app`. Use a bare address on `mail.delvane.app`. |
| `RESEND_INVITATION_LANGUAGE` | Optional deployment setting. Defaults to `bilingual`. Use `hu` or `en` for a single-language invitation. |
| `RESEND_WEBHOOK_SECRET` | The signing secret from this webhook's details page. |
| `DELVANE_GUEST_PUBLIC_ORIGIN` | `https://<approved-guest-host>`, using the actual hostname with a trusted HTTPS certificate and no path or port. |
| `RESEND_TEST_RECIPIENT` | The owner's exact mailbox address for the controlled trial. It limits both approval and dispatch to that address. |
| `RESEND_HTTPS_PROXY` | For the isolated Hetzner layout, the internal CONNECT proxy origin as `http://<proxy-name>:<port>`. |

The owner enters the two secret values directly into the approved runtime secret store and maps them to the backend environment. For a self-managed lab, use a root-owned, mode `0600` service environment file outside Git and the build context. Keep secrets out of shell commands, chat, screenshots, compose files, logs and diagnostics. Limit service and Docker administration access because those operators can inspect environment variables. Use the webhook signing secret separately from the sending key. The legacy normalized callback and its signing secret are for other adapters. The native Resend callback can keep accepting receipts when sending is paused if the provider selection and webhook secret remain configured. Restart the backend when changing these settings.

## Create the webhook in the dashboard

1. On the approved guest HTTPS ingress, add only `POST /api/public/guest-delivery/resend-webhook` for Resend alongside the existing [guest page and asset allowlist](GUEST_COMMUNICATION_01.md). Preserve the raw bytes and `svix-id`, `svix-timestamp` and `svix-signature` headers. Keep operator APIs, docs, health, database and government routes private. Disable request-body and URL logging for guest web and webhook paths.
2. Open **Webhooks → Add Webhook** in Resend. Paste `https://<approved-guest-host>/api/public/guest-delivery/resend-webhook` and subscribe to `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.failed` and `email.suppressed`. Save, open the webhook details and have the owner store its signing secret as `RESEND_WEBHOOK_SECRET`. This uses the dashboard and the existing sending-only key. [Create a webhook](https://resend.com/docs/webhooks/create-webhook) · [Verify webhook requests](https://resend.com/docs/webhooks/verify-webhooks-requests)
3. Delvane verifies the Svix HMAC over the original body within a five-minute timestamp window and deduplicates by the signed event ID. It correlates an early receipt using the invitation tag and other receipts using the stored Resend email ID. A signed delayed event means Resend is still handling delivery. Delvane sends no second email for that event. **Delivery confirmed** means the recipient's mail server accepted the message. [Svix signing format](https://docs.svix.com/receiving/verifying-payloads/how-manual) · [Resend event types](https://resend.com/docs/webhooks/event-types)

## Existing Hetzner UAT and first invitation

1. In Resend, open **Webhooks → Add Webhook**. Enter `https://guest.delvane.app/api/public/guest-delivery/resend-webhook`. Select `email.sent`, `email.delivered`, `email.delivery_delayed`, `email.bounced`, `email.failed`, and `email.suppressed`. Save and open the webhook details to get the signing secret. Keep open and click tracking off on `mail.delvane.app`. The first public webhook check can wait until the paused configuration is applied.
2. In the existing pinned PowerShell SSH session, use `su -` and stop any active Windows UAT relay before applying the package. Copy the staged `resend-trial-v2.sh` into `/root/resend-trial.sh`, verify its SHA-256 against the locally reviewed manifest and run `bash /root/resend-trial.sh`. It tests the live relay before restarting the app or prompting. Enter the existing webhook signing secret and one owner-controlled mailbox if the root-only settings file is absent. The prompts are masked and sending stays disabled.
3. The setup replaces only the app container and reconnects the existing connector to the recreated Unix socket. It keeps the existing PostgreSQL volume, tunnel, DNS, bridge and government firewall policy. The separate Resend relay binds inside the app's network namespace at `127.0.0.1:3128`. Its host-side service runs under its own UID. It requires the exact CONNECT authority and TLS server name `api.resend.com`, and its nftables table permits only the setup-time public IPv4 addresses on TCP 443. The TLS session remains end-to-end. Setup checks the TLS handshake without calling the email API. It also verifies a signed local receipt, rejection after changing one body byte, and blocked private routes. If the addresses change, sending can fail until the scoped policy is refreshed.
4. For the **later authorized send**, run `bash /root/resend-trial.sh arm`. This checks for pending Resend work before starting a sending-enabled app limited to the configured mailbox. If needed, provide the existing API key from `.env.local` at the masked prompt. Reopen the Windows UAT relay. In Delvane Business, confirm one future reservation with one fictional guest and the configured address as the booking's invitation address. In **Reception**, approve the prepared invitation once. Watch the distinction between **Provider accepted** and **Delivery confirmed**, check your own inbox, and open only the fictional check-in link. If delivery is uncertain, inspect the existing record before taking any retry action.
5. Run `bash /root/resend-trial.sh pause` to disable sending again. Signature verification and delivery receipts remain active. The connector restarts during both app setting changes, so close the Windows relay before either transition and reopen it afterward. NTAK and VIZA stay disabled throughout.

## Minimum Hetzner network change for a later approved trial

Keep the application and PostgreSQL on their internal bridge. Provide the application access to a dedicated CONNECT proxy over a private network with no published ports. Only the proxy gets external egress. Its ACL must allow only `CONNECT api.resend.com:443` and deny all other hosts, IP literals, ports and methods for both IPv4 and IPv6. Allow the proxy to use the approved DNS resolver. Keep direct external routes and DNS unavailable to the application. The proxy tunnels TLS without termination, keeps request and response content out of logs, and rejects private or link-local resolutions for the API hostname. Delvane pins the API host and uses normal TLS certificate and hostname verification inside the tunnel.

Before sending, verify the app has no direct default route, accepts only the private proxy path for mail egress, and keeps PostgreSQL private. Review the proxy's default-deny rules and test a synthetic forbidden CONNECT target. Keep NTAK and VIZA application gates disabled and the government destinations outside both the proxy ACL and network egress policy. Provide the webhook and guest page through the separate restricted HTTPS ingress. No network or server change was made as part of this integration.

## Send one controlled test email

1. After the network and webhook are in place and the updated backend is approved for use, set `RESEND_TEST_RECIPIENT` to the owner's mailbox. Sign in as the owner of a fresh synthetic property. Confirm the queue has no pending invitations and both government transmission controls are disabled. Use **Domains → mail.delvane.app → Configure** to confirm click and open tracking are off.
2. Set `DELVANE_GUEST_EMAIL_ENABLED=1` and restart the isolated backend. In Delvane Business, create one fictional direct reservation with a future check-in date, one fictional guest and the same mailbox in **Invitation email**. In **Reception → Scheduled**, choose that invitation and click **Approve and queue email** once.
3. Confirm Reception reaches **Provider accepted** and verify the matching message under **Emails** in Resend. Confirm that the dashboard shows a successful webhook request to the configured endpoint and that Reception reaches **Delivery confirmed**. If it shows **Delivery delayed at recipient server**, wait for the provider's next event. Inspect the dashboard status if the invitation fails or becomes unconfirmed.
4. Open the one message in the owner's mailbox. Check the sender, both languages and the guest HTTPS link. If testing the guest form, use fictional details only. Cancel the booking and verify the link is rejected if it has not been used. Set `DELVANE_GUEST_EMAIL_ENABLED=0` and restart the backend to pause further sends. Leave the trial mailbox restriction in place during pilot testing.

## Local verification

The shared backend run passed 63 tests, and the final delivery-only run passed 20 tests with an offline fake Resend transport. Coverage includes retries with an identical payload, provider rejection, early and duplicate receipts, wrong and stale signatures, cancellation, inspection of logs and owner-facing status for secrets, and both localized templates. The existing guest-delivery rehearsal passed on disposable PostgreSQL 17.12 through a backend restart. Flutter analysis was clean and all 21 targeted Reception and reservation widget tests passed. No schema migration, live email, server change, deployment or Git commit was required.
