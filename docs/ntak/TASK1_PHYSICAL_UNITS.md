# Task 1 physical accommodation units

Implemented 2026-11-19. Scope: physical unit records and dated OOO/OOS only. No physical reservation allocations, Flutter changes, guest events, financial ledger or SOAP changes were made in this task. Existing uncommitted NTAK work was preserved.

## Model and migration

Migration **3074**, `physical_units.migrate`, runs through existing `init_db` after room types and prior migrations. Creates `physical_units`, `physical_unit_versions`, `physical_unit_periods` and a property lookup index. No existing inventory rows are converted, deleted, reseeded or modified. No migration was executed on the persistent development workspace.

A stable unit belongs to one tenant/property. Version records hold an effective business date, the existing local room-type ID, building and unit number, official NTAK classification, single/double/extra bed counts, active state, reason, actor and recorded timestamp. Regular places = single beds + twice double beds. Extra beds remain separate. Official classification values are read from the supplied daily-close embedded XSD's `LakoegysegTipusType`; no fixture-specific classifications are hardcoded.

New versions must follow prior effective dates; a same-date or earlier overwrite is rejected. This deliberately preserves historical identity, mapping and capacity. Building/unit labels are reserved within a property across history. There is no destructive delete. Deactivation is a new version with `active=false`; periods must be ended/cancelled first. A single apartment uses one physical unit linked to its existing room type, without a hotel hierarchy or multiple-unit requirement. Building and unit labels and bed counts must be explicitly supplied, including for a single apartment.

OOO and OOS periods use **inclusive** `date_from`/`date_to` business dates. Overlapping periods for one unit are rejected, including overlap between different states. Unit must be active throughout. Cancellation records `cancelled_from` (inclusive return-to-service date), actor/time/reason while retaining original dates and state. A period can be cancelled only once; subsequent state changes use new periods. Historical corrected operational state can be queried by date; the original declaration and cancellation record remain visible in history.

Official basis: interface v9.07 glossary p24 defines OOO as unsuitable/unrentable (e.g. renovation), OOS as temporarily closed (e.g. short maintenance). Sections9.2.12–13 pp76–77 require distinct counts, both states included in unavailable-room details, and unavailable list count = OOO+OOS. Section9.2.15 p78 excludes both from available capacity. The validation workbook requires 4 units,10 regular places,1 extra. These are offline fixtures only. No reporting message is generated by this task.

## API

Prefix: `/api/properties/{property_id}/physical-units`.

| Method/path | Operation |
|---|---|
| GET prefix `?business_date=YYYY-MM-DD` | Retrieve effective versions, including inactive records where effective |
| GET `/capacity?business_date=YYYY-MM-DD` | Effective active physical units; total/OOO/OOS/operationally available unit, regular-place and extra-place counts |
| POST prefix | Create stable unit and initial version |
| PUT `/{unit_id}` | Append full dated version; also safe deactivate/reactivate using active flag |
| GET `/{unit_id}/history` | All versions and original/cancelled operational periods |
| POST `/{unit_id}/periods` | Add dated OOO or OOS period |
| POST `/{unit_id}/periods/{period_id}/cancel` | Record dated return to service; original period retained |

Create/PUT fields: `effective_from`, `room_type_id`, `building`, `unit_number`, `classification`, `single_beds`, `double_beds`, `extra_beds`, optional `active` (default true), `reason`. Bed counts must be strict nonnegative integers, regular capacity positive; boolean/fractional bed counts rejected. Period fields: `state` (`OOO`/`OOS`), `date_from`, `date_to`, `reason`. Cancel fields: `effective_from`, `reason`. Unknown fields rejected.

Owners can write; owners/managers can read under the existing organization-wide property permission model. Every unit, property, room-type and period lookup is scoped to the authorized property and tenant. Workers receive no access. Existing authentication/CSRF middleware applies, with audit events on changes. Property-row lock serializes writes for same-property identity/period validation on SQLite/PostgreSQL. No new property grants model was introduced.

## Compatibility and limits

Unit's room-type reference preserves its connection to existing Channex mappings; no second provider mapping is created. Physical records and OOO/OOS **do not change aggregate stock, channel availability, reservation overlaps or trigger Channex updates**. Existing aggregate inventory remains the channel source of truth until physical allocations and a deliberate stock-reconciliation change are implemented. This avoids adding physical quantities to existing aggregate quantities or decrementing stock twice.

Capacity response includes `aggregate_comparison` per active room type, showing mismatches between declared physical records and current aggregate quantities. It never silently resolves a mismatch. Empty physical inventory means not configured, not a verified zero-room property. Historical aggregate comparison is with **current** aggregate stock; physical dated counts use effective versions. There is no claim to historical Channex inventory reconstruction.

`available` in this API means active and not OOO/OOS; it does not subtract booked/sold units. `physical_inventory_only`, `allocation_supported=false`, `capacity_basis` and `availability_basis` make this distinction explicit. Reservations cannot yet be checked against physical unit periods; that requires Task2 allocations. Counts should not be used as final daily-close occupancy totals yet.

Regular units with zero sleeping places are rejected. Per bed-count upper guard is10000 (input guard, not an official capacity classification). Backdated new versions are allowed only if after that unit's latest effective version, with reason/audit; overwriting historical versions/cancellation records is not supported. Read history exposes actor/reason to authorized operators. No GUI is added in Task1. PostgreSQL SQL follows the existing adapter but was not executed against a PostgreSQL service.
